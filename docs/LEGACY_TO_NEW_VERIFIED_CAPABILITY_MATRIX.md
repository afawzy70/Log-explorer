# Legacy-to-New Verified Capability Matrix

Owner-directed reconciliation: every capability the OLD app (`legacy-app-docs/`) had or
intentionally designed, checked against the actual NEW source code in this repository
(`backend/`, `frontend/`) — not inferred from similarly-named components. This replaces
`legacy-app-docs/audit/AUDIT-14-CAPABILITY-MATRIX-OLD.md`'s `Putative NEW (UNVERIFIED)` column
with real evidence.

**How NEW evidence was gathered:** direct inspection of the current NEW source tree (`grep`/file
reads performed this session), cross-referenced against this session's own build history for
every NEW file (Phases A–M, all real, all tested — see `docs/verification/PHASE_<X>_REPORT.md`
for the commands/output behind each). Every NEW claim below cites a real file and, where one
exists, a real test. Where a claim could not be verified from static source alone (e.g. exact
live-browser behavior not covered by an existing test), it is marked `NEEDS_LIVE_VERIFICATION`
rather than asserted.

**Status legend:**
- `NEW_FULL` — capability fully present and working in NEW, verified.
- `NEW_PARTIAL` — present but narrower, less automatic, or reachable only in some cases.
- `NEW_MISSING` — not present in NEW at all.
- `NEW_CHANGED_BETTER` — NEW does the same job differently, and the NEW way is verifiably safer/simpler/more correct.
- `NEW_CHANGED_WORSE` — NEW does the same job differently, and the NEW way is a real regression.
- `SUPERSEDED_BY_OWNER_DECISION` — CLAUDE.md/HANDOVER.md explicitly chose a different, deliberate behavior; OLD's version is not being reintroduced.
- `NEEDS_LIVE_VERIFICATION` — static evidence is inconclusive; needs a real browser/backend check before deciding.
- `UNKNOWN` — insufficient evidence either side; flagged for follow-up.

**UX parity / Backend parity columns:** `NEW_BETTER` / `EQUIVALENT` / `NEW_WORSE` / `N/A` (used only where the row is meaningfully about workflow efficiency or backend correctness respectively).

**Priority:** P0 (core capability missing/incorrect security or architecture) · P1 (significant workflow regression or high-value missing feature) · P2 (productivity/usability improvement) · P3 (optional, low impact). Priority reflects value, not implementation ease.
