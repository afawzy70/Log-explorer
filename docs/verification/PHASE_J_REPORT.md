## Architecture

**Backend — a new streaming transport alongside the existing request/response search path, reusing the same masking, guardrail, and cancellation primitives rather than duplicating them:**

- **`source/LogSource.java`**: a new default method `follow(FollowRequest)` returning `Flux.error(UnsupportedOperationException(...))` — every existing `LogSource` implementation keeps compiling unchanged, and only sources that genuinely implement it (Docker, Fixture) advertise `liveTail: true`.
- **`core/model/FollowRequest.java`**: `sourceId` + `services` only — deliberately the same minimal, non-sensitive shape the URL itself carries (see "Security check" below); there is no field for a search value, because live tail's own scope never accepts one.
- **`source/fixture/FixtureLogSource.java#follow`**: `Flux.interval(700ms)` ticking a deterministic generator — one event per tick, a burst of 5 every 6th tick — filtered by the requested services. **`FixtureCorpusGenerator#generateLiveLine(seed, globalIndex, timestamp)`** deliberately recomputes only the one bounded 700-line cycle the requested index falls in (never the whole growing history), so per-tick cost stays constant no matter how long a live session runs — the same "no unbounded scans" principle (CLAUDE.md §4 "Bounds") applied to an open-ended stream instead of a bounded query.
- **`source/docker/DockerFollowCallback.java`**: a new, standalone `ResultCallback.Adapter<Frame>` — deliberately **not** sharing code with the existing `DockerFrameCollectingCallback` (used by historical search), because that callback's whole job is collecting a bounded list of frames up to a byte cap before returning; a live follow has no such bound and must instead emit each line **immediately** as it arrives. Reusing one class for both shapes would have meant a boolean flag silently changing its fundamental behavior — two small, honest classes instead.
- **`source/docker/DockerLogSource.java#follow`**: lists containers on `Schedulers.boundedElastic()` (CLAUDE.md §5's blocking-Docker-call rule), then bridges docker-java's callback-based `followLogs` into a `Flux` via `Flux.create(..., FluxSink.OverflowStrategy.BUFFER)`. Cancellation is proven, not assumed: `sink.onDispose(() -> closeAll(callbacks))` closes the real `Closeable` docker-java hands back through `ResultCallback.Adapter#onStart`, and `DockerLogSourceTest#cancellationClosesTheUnderlyingDockerFollowCallback` captures that mock and verifies `.close()` is actually called after disposing the Reactor subscription.
- **`api/live/LiveTailService.java`**: the composition point — `source.follow(...)` is wrapped in `onBackpressureBuffer(serverBufferSize, ..., DROP_OLDEST)` (an honest, counted server-side bound), merged with a periodic `status` heartbeat carrying that drop count, capped by `LiveTailGuard` (a semaphore mirroring the existing `ConcurrencyGuard`'s exact shape) at a configurable max concurrent tails, and bounded overall by `.take(connectionTimeout)`. A source whose `capabilities().liveTail()` is false is rejected outright via the existing `GuardrailViolationException` mechanism (`LIVE_TAIL_NOT_SUPPORTED`), reusing `GlobalExceptionHandler` rather than inventing a second error path.
- **`api/live/LiveTailController.java`**: `GET /api/v1/logs/live?sourceId=...&services=...`, `produces = TEXT_EVENT_STREAM_VALUE`. `EventSource` (the browser's native SSE client) only supports `GET` with no custom body — which is exactly why `FollowRequest`'s shape is deliberately minimal: there is nowhere a search value or filter could go even if someone tried to add one later without also widening the URL's own contract.
- **`config/LiveTailProperties.java`**: `maxConcurrentTails`, `connectionTimeout`, `heartbeatInterval`, `serverBufferSize` — all externally configurable (`logexplorer.live.*` in `application.yml`), nothing hardcoded.

**Frontend — `features/live/**`, mirroring the journey view's "replaces `ResultsPanel`, never coexists with it" pattern from Phase I:**

- **`useLiveTail.ts`**: the full lifecycle hook. Owns the real `EventSource`, two independently-bounded buffers (the 1,000-cap visible list and a separately-capped paused buffer — see "Bounds" below), and five **distinct, never-conflated** counts: `totalReceived`, `bufferedCount`, `clientDroppedCount` (this client's own 1,000-cap eviction), `serverDroppedCount` (the backend's own bounded-buffer overflow, arriving via the `status` SSE event). Pause keeps the real connection open — only Stop actually closes it, so Resume never needs to reconnect. Unmounting always closes it (`useEffect(() => closeEventSource, [closeEventSource])`).
- **`LiveTailPanel.tsx`**: renders in place of `ResultsPanel`/`JourneyView` whenever live mode is active (see `App.tsx`). Deliberately **not** the seven-column results table — a pulsing red "LIVE" badge, its own accent border, and `JourneyEntryRow` (reused from Phase I) for individual events, so live tail is visually unmistakable from historical search at a glance, not just by reading a label.
- **`Toolbar.tsx`**: a "Live" button, shown only when `state.selectedSource?.capabilities.liveTail` is true (the same capability-gating pattern established in Phase F/G/H — the frontend never infers what a source can do), positioned before "More filters." Its `onClick` is wired directly to `live.start(...)` in `App.tsx` — **one click both opens the panel and begins streaming**; the panel's own "Start" button exists for the separate case of restarting after Stop/Error, not as a second step after opening.
- **`App.tsx`**: a source-change effect closes any active live session (`live.exit()`) the moment `state.selectedSourceId` changes — HANDOVER.md §18.4's "source navigation... closes stream," verified for real in the browser (see below).

## A real bug found and fixed via genuine backpressure testing, not code review

While writing a deterministic test for "the server-side buffer really does drop oldest events under overflow," `StepVerifier`-based attempts kept failing to reproduce genuine dropping — `Flux.merge`'s own prefetch and various consumers' eager demand made the configured `serverBufferSize` bound unreachable in a test harness. Chasing that down empirically (via standalone Reactor probe scripts, not guesswork) surfaced something more serious than the original test problem: **`Flux.interval`, used for the heartbeat/status channel, throws `OverflowException: Could not emit tick... due to lack of requests` under genuine small/slow downstream demand.** Because the heartbeat is merged into the same stream as the log events, this exception doesn't just skip a tick — it **kills the entire live-tail connection** for any real, sufficiently slow SSE client, silently converting "you missed a heartbeat" into "your whole session is now dead."

**Fix.** `.onBackpressureLatest()` added to the status `Flux` in `LiveTailService.java` — a stale heartbeat tick can safely be superseded by a fresher one; only the most recent `droppedCount`/`serverTime` value ever matters, so dropping intermediate ticks under backpressure is correct behavior, not data loss.

**Regression test.** `LiveTailServiceTest#theConnectionSurvivesASustainedSlowConsumerWithoutErroringOutFromTheHeartbeatAlone` — a raw `org.reactivestreams.Subscriber` requesting a small, fixed demand exactly once (chosen after `StepVerifier`'s own eager consumption proved unable to create genuine sustained backpressure through the full merge+guard+take pipeline), proving the connection survives rather than erroring. The original buffer-overflow test itself was rewritten around the same fixed-demand subscriber to prove the more meaningful, provable invariant "a slow consumer never receives more than it actually requested," rather than chasing Reactor's exact internal drop-oldest sequencing through three composed operators, which proved unreliable to pin down deterministically.

## Scope delivered

4. **Bounded backend buffer, heartbeat, timeout, max concurrent tails** — all four, config-driven, in `LiveTailService`/`LiveTailProperties`/`LiveTailGuard`. Includes the real heartbeat-crash bug found and fixed above.
5. **Bounded frontend buffer, 1,000-event initial display cap, dropped/buffered counts visible** — `useLiveTail.ts`'s `VISIBLE_CAP` eviction plus a separately-bounded paused buffer; `LiveTailPanel.tsx` shows all three drop/buffer counts as distinct, never-conflated values.
6. **Start/pause/resume/stop lifecycle; unmount and source-navigation close the stream** — `useLiveTail.ts`, `LiveTailPanel.tsx`, `App.tsx`'s source-change effect.

## Security check for this phase

- **Never a search value, token, or raw identifier in the URL.** `FollowRequest`'s shape (`sourceId` + `services`) and `LiveTailController#live`'s query parameters are the *only* things live tail's URL can ever carry — there is no field anywhere in the request path for a search value to flow through, let alone leak. Proven directly with a real `curl` against the running backend and `useLiveTail.test.ts#start() opens a real EventSource...`.
- **Masking applied before every event reaches the stream, at the same single boundary as historical search.** `LiveTailService#follow` maps each `CanonicalLogEvent` through the existing `EventMapper#toDto` (the same masking boundary Phase B established) before wrapping it in an SSE `ServerSentEvent` — there is no second, parallel masking path to keep in sync or accidentally bypass. `LiveTailServiceTest#everyEmittedLogEventIsMaskedBeforeItEverReachesTheStream`; confirmed for real over HTTP in `LiveTailControllerTest` and via a real `curl` showing `"cif":"****"` etc. in the live wire payload; the frontend browser test scans the entire rendered live panel's text for an unmasked sensitive value.
- **Docker access stays strictly read-only.** `DockerLogSource#follow` calls only `ReadOnlyDockerClient#followLogs`, itself a thin wrapper around docker-java's own read-only `logContainerCmd(...).withFollowStream(true)` — no start/stop/create/remove/exec call exists anywhere in the live-tail path. `ReadOnlyDockerClientMethodSetTest` continues to lock the facade's entire method set (now including `followLogs`, added deliberately after confirming it contains no mutating keyword).
- **Blocking Docker calls stay off the WebFlux event loop.** Container listing in `DockerLogSource#follow` runs on `Schedulers.boundedElastic()`, matching CLAUDE.md §5's rule and every prior Docker-adapter phase's own practice.
- **`dangerouslySetInnerHTML`**: `LiveTailPanel.tsx` renders every event via the already-audited `JourneyEntryRow` (Phase I) — no new HTML-injection surface introduced. `noDangerousHtml.test.ts` (Phase H) continues to pass over every new file.
- **Nothing new written to `localStorage`/`sessionStorage`/the URL beyond `sourceId`/`services`.** Live-tail state lives in `useLiveTail`'s React state and refs only.
- **Bounded everywhere.** Server buffer (`onBackpressureBuffer`, config-driven size), connection timeout (`.take(...)`), concurrent-tail cap (`LiveTailGuard`), frontend visible cap (1,000), and a separately-bounded paused buffer — no unbounded array, buffer, or DOM row list anywhere in the live-tail path (CLAUDE.md §4 "Bounds").
