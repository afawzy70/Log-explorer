# Source Experience Parity — Docker / OpenShift primary Search

`MISSION=SOURCE_EXPERIENCE_PARITY_DOCKER_OPENSHIFT`. Implements the owner requirement recorded (but not
previously implemented) at `docs/governance/OWNER_REQUIREMENTS_REGISTER.md` §28: OpenShift, once connected,
must use the exact same primary Search workspace, Search button, Results table, and Inspector as Docker —
never a second, OpenShift-specific pipeline.

## 1. Current-state gap (before this mission)

- OpenShift's Workload/Pod/Container scope selection lived entirely inside **Settings**
  (`OpenShiftSettingsPanel.tsx`'s own `OpenShiftScopeControls`), reachable only by opening the Settings
  workspace — never from Search.
- The Search `Toolbar` rendered `ServiceMultiSelect` (Docker's own control) **unconditionally**, with no
  capability gate, for every source including OpenShift — even though OpenShift declares
  `serviceDiscovery=false` and its service-discovery endpoint always returns an empty list. This meant
  OpenShift's Search toolbar showed a functionally dead "All services" control instead of its own real scope
  equivalent.
- To change Project/Workload/Pod/Container, a user had to leave Search, open Settings, make the change, then
  return — the "Search scope can be changed without returning to Settings" requirement did not hold.
- Settings' own scope-editing state and Search's toolbar were two separate surfaces that could, in principle,
  present different views of the same backend session (never literally out of sync, since both ultimately read
  the same `GET /scope`, but the *editing* authority lived somewhere Search itself couldn't reach).

## 2. Backend contract discovery (Phase 0 — no backend semantics changed)

Verified directly against the code at the start HEAD, not assumed:

1. **Scope state model**: server-side, **session-held**, not request-carried. `OpenShiftSession`
   (`backend/src/main/java/com/logexplorer/source/openshift/OpenShiftSession.java`) holds one immutable
   `Snapshot` (`selectedProject`, `scope: OpenShiftScope`, `generation`). `OpenShiftScope` is a nested
   immutable record: `workloads`, `workloadKindOutcomes`, `selectedWorkload`, `pods`, `podScopeComplete`,
   `selectedPod`, `containers`, `selectedContainer`.
2. **Workload kinds**: exactly `DEPLOYMENT`, `DEPLOYMENT_CONFIG`, `STATEFUL_SET`, `DAEMON_SET`
   (`WorkloadKind.java`). Jobs/CronJobs explicitly deferred.
3. **Pod cardinality**: single, optional. `OpenShiftScope.selectedPod: String` (not a list);
   `selectOpenShiftPod(pod: string | null)`. The owner requirement's "optional Pod(s)" is satisfied truthfully
   as **one optional selected pod** — no fake multi-select was built over this single-pod API.
4. **Container cardinality**: single, optional, same shape as pod.
5. **Parent→child invalidation**: already fully implemented **server-side** (`OpenShiftScope`'s `with*`
   methods, `OpenShiftSession`'s selection methods) — project change replaces the whole scope; workload change
   clears pod+container; pod change clears container. This mission's frontend mirrors that same invalidation
   in its own UI state for immediate responsiveness, but the backend session remains the one authority.
6. **Search reads committed server-side scope**, never a request-carried field. `SearchRequestDto` has zero
   OpenShift-specific fields. `OpenShiftLogSource.search()`'s own doc comment states it "always reads live
   target identity from `OpenShiftSession#scope()` itself... never from caller-supplied fields." This is why no
   backend change was needed to wire the new Search-side controls in: they call the same mutation endpoints
   Settings already called, and Search's own request body is untouched.
7. **Live** follows the identical pattern — `follow()` ignores `FollowRequest`'s Docker-shaped fields and reads
   the current session scope.
8. **`contextTargetProof`**: opaque, HMAC-signed, bound to `(sourceId, connectionGeneration, namespace, pod,
   container)`, generated by `ContextTargetProofCodec`, invalidated on reconnect. Travels as an opaque string
   on `LogEvent.contextTargetProof`, round-tripped verbatim on a later context request. Untouched by this
   mission.
9. **RBAC / PARTIAL discovery**: `WorkloadDiscoveryDto.status`: `SUCCESS | PARTIAL | FORBIDDEN` (from per-kind
   `AVAILABLE | UNAVAILABLE_RESOURCE_TYPE | FORBIDDEN | ERROR`); `PodDiscoveryDto.status`: `COMPLETE | PARTIAL`.
   Never collapsed into an empty list. Preserved verbatim in the relocated UI.
10. **Capabilities**: OpenShift declares `(historicalSearch=true, liveTail=true, rawLogQL=false,
    serviceDiscovery=false, queryStatistics=false, contextView=true, composeProjectScoping=false,
    originalSchemaSampling=true)`. `serviceDiscovery=false` is the capability this mission now actually gates
    `ServiceMultiSelect` on (see §3).
11. **Field mapping scope**: `OpenShiftLogSource.resolveMappingScopeLabel()` returns the session's
    `selectedProject` directly — Field Mapping is always keyed to the session's current project, already wired
    through `App.tsx`'s `resolveMappingProject`, untouched by this mission.
12. **Guardrails**: stale-response protection already exists server-side via `generation`/`expectedProject`/
    `expectedWorkload`/`expectedPod` guards in `OpenShiftSession`. The new frontend hook adds its own
    client-side generation counters (mirroring the existing pattern in `useSearchState.ts`'s own search/service
    discovery) so a slow discovery response can never overwrite a newer selection in the UI either.

**No backend/Java file was changed.** Every gap above was a frontend composition problem — the backend already
had the exactly correct, single-authority contract this mission's UX requirement needed.

## 3. Implemented architecture

### Frontend files

| File | Role |
|---|---|
| `frontend/src/features/search/openshift/workloadKindLabels.ts` | `WORKLOAD_KIND_LABELS` + `workloadOptionValue`/`parseWorkloadOptionValue`, extracted so Shell's `ScopeTrail`, the new Search control, and Settings' read-only summary share one label set |
| `frontend/src/features/search/openshift/OpenShiftScopeControls.tsx` | The Workload → Pod → Container `<select>` trio (loading/empty/FORBIDDEN/PARTIAL states preserved byte-for-byte from the old Settings implementation), relocated with a new compact toolbar-row CSS module |
| `frontend/src/features/search/openshift/useOpenShiftScopeEditor.ts` | The mutation/discovery hook: calls the same `selectOpenShiftProject`/`selectOpenShiftWorkload`/`selectOpenShiftPod`/`selectOpenShiftContainer` APIs Settings used to call directly, then calls `onScopeChanged` (the already-lifted `useOpenShiftScopeSummary.refresh`) — never a second scope authority. Seeds its initial Workload/Pod/Container selection from that same lifted summary (a genuine improvement: the old Settings panel explicitly did not restore prior selections on reopen; this does) |
| `frontend/src/features/search/openshift/OpenShiftScopeSelect.tsx` | The Toolbar-facing composition: Project select + `OpenShiftScopeControls`, with not-connected / no-projects / connected states |
| `frontend/src/app/Toolbar.tsx` | Renders `OpenShiftScopeSelect` in place of `ServiceMultiSelect` when the selected source is OpenShift; `ServiceMultiSelect` is now gated by the `serviceDiscovery` capability (previously unconditional) |
| `frontend/src/features/settings/OpenShiftSettingsPanel.tsx` | No longer edits scope — shows it **read-only**, sourced from the same lifted `scope` prop, with a hint pointing to Search |
| `frontend/src/app/Shell.tsx` | Import path update only (`WORKLOAD_KIND_LABELS` moved) |
| `frontend/src/features/settings/SettingsWorkspace.tsx`, `frontend/src/app/App.tsx` | Thread the shared `openShiftScopeState.scope`/`.refresh` into both `Toolbar` (new: `onOpenShiftScopeChanged`) and `OpenShiftSettingsPanel` (new: `scope`) |

**No new component framework, no generic "source scope" abstraction was built.** Per the mission's own "two
clear implementations are sufficient" guidance, `Toolbar.tsx` contains exactly one `isOpenShift` conditional
choosing between the Docker pair (`ComposeProjectSelect` + `ServiceMultiSelect`) and the OpenShift control
(`OpenShiftScopeSelect`) — the same shape the file already used for `ComposeProjectSelect`'s own capability
gate.

### Single authority, not two

The backend session (`OpenShiftSession`) is the only place Project/Workload/Pod/Container selection is
authoritative. The already-existing `useOpenShiftScopeSummary` hook (lifted once in `App.tsx`) is the only
frontend read of that truth, shared by `Shell`'s `ScopeTrail`, the new `OpenShiftScopeSelect`, and
`OpenShiftSettingsPanel`'s read-only summary. Every mutation (from Search) calls the same
`openShiftScopeState.refresh` Settings' old mutations used to call — there is no second, parallel scope state
anywhere in the frontend.

## 4. Docker behavior (unchanged)

Docker's `Source → Compose project → Service` hierarchy, Include/Exclude mode, and Compose-project isolation
are untouched — `ComposeProjectSelect` and `ServiceMultiSelect` render exactly as before for any source whose
capabilities say so (now including the explicit `serviceDiscovery` gate that was implicitly-always-true for
Docker/Fixture anyway, so no visible change for them).

## 5. OpenShift behavior (new)

`Source → Project/Namespace → Workload → optional Pod → optional Container → Time/Severity/Query/More
Filters → Search`, in the exact same toolbar row Docker's own controls occupy, using the exact same `Search`
button, gated the same way it already was (`openShiftMissingRequiredScope`, unchanged). Project/Namespace
wording stays truthful to `discoveryApi` (`PROJECTS` vs `NAMESPACES`), matching the existing OS-1A/OS-1B
established copy verbatim.

## 6. Settings / Search responsibility split

- **Settings** (`OpenShiftSettingsPanel.tsx`): connection status, server/user/TLS/proxy, the `oc login` intake
  form, Disconnect, and now a **read-only** current-scope summary (Project/Workload/Pod/Container) with a hint
  directing the user to Search to change it.
- **Search** (`Toolbar.tsx` → `OpenShiftScopeSelect.tsx`): the only place Project/Workload/Pod/Container are
  now *selected*.

See `docs/verification/source-experience-parity/settings-openshift-readonly-scope-1440px.png` for the real
rendered read-only Settings view.

## 7. Security verification (unchanged, reverified)

- The pasted `oc login` command/token remains ephemeral/in-memory only, cleared immediately after submit —
  `OpenShiftSettingsPanel.test.tsx`'s own token-never-persisted tests are unchanged and still pass.
- No raw token is ever returned by any endpoint this mission touches.
- TLS verification, the loopback credential-intake guard, and `--insecure-skip-tls-verify` refusal are
  untouched (no code in that path was modified).
- `contextTargetProof` remains opaque — never displayed, never persisted, never logged; this mission did not
  touch the Inspector/Investigation/context code paths that carry it.
- Proxy semantics and RBAC/PARTIAL discovery truthfulness are preserved verbatim (moved, not rewritten).

### A real regression found and fixed by this mission's own E2E gate

`OpenShiftScopeControls.module.css`'s `.hint`/`.wrapper` used `white-space: nowrap` (copied from
`ComposeProjectSelect`, whose own hints are short). The Pod/Workload hints here are full sentences ("No pods
currently match this scope", "Some workload types could not be listed") — at 390px with a project/workload
selected, this produced a real, reproducible 17px page-level horizontal overflow. Found via the new E2E
suite's own 390px overflow assertion (flaky-looking at first because it only manifests once pod discovery
resolves and renders its hint — a real timing-dependent bug, not test flakiness), diagnosed with a DOM
measurement script identifying the exact overflowing element, and fixed by allowing the wrapper to `flex-wrap`
and the hint text to wrap normally. Re-verified with 6 repeated runs at zero overflow before and after.

## 11. Known limitations

- The Pod/Container cardinality is genuinely single-select, matching the backend contract exactly (§2.3/2.4) —
  this is not a limitation of the implementation, it is the truthful backend model, explicitly preserved per
  the mission's own "Cardinality Rule."
- `OpenShiftScopeSelect` fetches its own `fetchOpenShiftConnection()` on becoming active, separately from
  Settings' own fetch of the same endpoint when Settings opens. These never fire simultaneously (Settings and
  the Search toolbar are mutually exclusive takeover states in `App.tsx`), so this is not a "discovery storm" —
  it is one fetch per surface-open, the same pattern every other workspace in this app already uses.
- Real-cluster validation remains `NOT_AVAILABLE` per §9 — this does not fail the implementation; contract,
  unit, and E2E verification all pass.
